# Compact Wire Format

Status: Current active compact upload contract for official Honch SDKs and Capture.

The compact wire format is a strict binary upload contract. The goals are:

- smaller device-to-capture payloads than the old CBOR shape;
- one chunk transport for direct HTTP, relay, BLE, gateway, and companion flows;
- deterministic decoding in capture with a small parser surface;
- lossless expansion into the existing Honch event model after ingest;
- no JSON compatibility requirements on the device path.

This wire format is the SDK and gateway ingest contract.

## Endpoint

```text
POST /capture
Content-Type: application/vnd.honch.chunk
X-Honch-Project-Key: <project_api_key>
X-Honch-Stream-Id: <stream_id>        # required for multi-chunk HTTP uploads
X-Honch-Relay-Id: <gateway_id>        # optional
X-Honch-Relay-SDK-Platform: <platform> # optional
X-Honch-Relay-SDK-Version: <version>   # optional
```

The request body contains exactly one chunk frame.

`Content-Encoding` is not allowed for chunks. Compression can be added in a
future frame flag, but the current format starts with one deterministic binary
path.

The project key is sent as a transport credential and is not encoded in the
device message body. This keeps the device message reusable across direct and
relay transports without repeating a long token inside every message.

## Upload Model

Every upload uses the chunk frame, including direct Wi-Fi HTTP. A direct HTTP
upload that fits in one request sends a single final frame. Transports with
smaller MTUs split the same compact message into multiple frames.

Capture must accept:

- a single complete frame;
- an init frame followed by continuation frames for the same message;
- duplicate frames whose payload bytes match already stored bytes.

Capture must reject:

- unsupported protocol versions;
- unsupported source types;
- nonzero reserved bits;
- offset mismatches;
- message ID collisions with different bytes;
- CRC failures;
- messages that exceed configured limits;
- frames for expired or unknown partial messages.

## Chunk Frame

All integer fields inside the frame are unsigned LEB128 varints unless noted.
CRC16 is little-endian CRC-16/CCITT-FALSE over the complete unchunked compact
message bytes, not over the frame header.

```text
header      u8
message_id  uvarint
if init and more: total_message_length uvarint
if continuation:  offset uvarint
payload     remaining bytes, excluding final crc
if final:   crc16_le
```

The frame is length-delimited by the carrier:

- HTTP: `Content-Length` of the request body;
- BLE or serial: the link-layer packet length;
- file or log export: the stored record length.

There is no payload length field in the frame. The carrier already
length-delimits each frame.

### Header Byte

```text
bits 0-1: protocol_version_code, always 2 for the compact wire format
bits 2-4: source_type
bit 5:    continuation, 0 for init/single, 1 for continuation
bit 6:    more, 1 if at least one later frame is required
bit 7:    reserved, must be 0
```

Source types:

| Value | Source | Description |
|------:|--------|-------------|
| 0 | events | Compact event message |
| 1-7 | reserved | Requires a spec update |

### Init, Continuation, And Single Frames

A single-frame upload has `continuation=0` and `more=0`:

```text
header message_id payload crc16_le
```

The first frame of a multi-frame upload has `continuation=0` and `more=1`:

```text
header message_id total_message_length payload
```

A middle continuation has `continuation=1` and `more=1`:

```text
header message_id offset payload
```

The final continuation has `continuation=1` and `more=0`:

```text
header message_id offset payload crc16_le
```

`offset` is the byte offset of `payload` within the complete compact message.
The init frame payload always starts at offset `0`.

### Message IDs

`message_id` is generated by the SDK or relay sender and is scoped to:

```text
project + stream_id + source_type
```

For direct single-frame HTTP, `X-Honch-Stream-Id` is optional. For any
multi-frame HTTP upload, it is required. For BLE, serial, or gateway-local
links, the stream identity may come from the link-layer peer identity.

SDKs should use a monotonically increasing 32-bit message ID seeded at boot.
Gateways may replace the message ID when re-chunking a fully received device
message, but must not change the compact message bytes.

## Relay Uploads

React Native relay uploads completed device messages to the canonical capture
endpoint:

```text
POST /capture
Content-Type: application/vnd.honch.chunk
X-Honch-Project-Key: <project_api_key>
X-Honch-Stream-Id: <relay_stream_id>
X-Honch-Relay-Id: <mobile_relay_id>
X-Honch-Relay-SDK-Platform: react-native
X-Honch-Relay-SDK-Version: <package_version>
```

Firmware relay chunks carry compact message bytes. The mobile relay validates
and reassembles relay frames, durably stores the completed compact message,
then uploads one or more compact wire-v2 HTTP chunk frames to `/capture`. The
relay may re-chunk for HTTP, but it must not rewrite the compact message body.

### Sender Rules

- Send frames for a message in ascending offset order.
- Do not interleave two messages on the same stream/source pair.
- Keep the source message pending until the receiver acknowledges the complete
  message.
- Retry a failed message from offset `0`.
- Use the smallest MTU-safe frame size for the active transport.
- Include CRC16 only on the final frame.
- Expect `202` on each non-final frame (stored, send next) and `204` on the final
  frame (message accepted). Handle any other status per the Response Codes table:
  `409` retries from offset `0`; `413` (too large) is a permanent drop, not
  retryable; `429`/`5xx`/network errors retain and retry with backoff.

### Receiver Rules

- Reassemble by project, stream ID, source type, and message ID.
- Store partial messages durably before acknowledging non-final frames.
- Accept an exact duplicate frame without appending bytes twice.
- Reject a duplicate frame with different bytes for the same offset.
- Validate CRC16 before decoding the compact message.
- Decode and enqueue events only after the final frame passes CRC.
- Expire incomplete messages after 24 hours unless capture config overrides it.

## Compact Event Message

The source type `events` payload is a compact event message. It is not CBOR,
JSON, MessagePack, or protobuf. It is a strict Honch binary grammar using
varints, a string table, numeric keys, and typed values.

All integers are LEB128 varints unless noted. Signed integers use ZigZag:

```text
zigzag(n) = (n << 1) ^ (n >> 63)
```

Strings are UTF-8 byte strings. Capture must reject invalid UTF-8.

### Message Layout

```text
format_version  uvarint   # always 2
message_kind    uvarint   # 1 = event_batch
flags           uvarint
base_time_ms    uvarint
string_table
batch_context
events
```

`flags` is a bitset. All reserved bits must be zero.

| Bit | Name | Meaning |
|----:|------|---------|
| 0 | context_promotes_properties | Capture expands message context into each event's properties |
| 1-63 | reserved | Must be zero |

SDKs must set `context_promotes_properties`.

`base_time_ms` is the epoch millisecond timestamp used as the reference for all
event deltas in the message.

### String Table

```text
string_count uvarint
repeat string_count:
  byte_length uvarint
  utf8_bytes
```

The string table stores event names, custom property names, string values, and
context string values.

Rules:

- Strings must be unique within the table.
- The first string has index `0`.
- Empty strings are allowed only for property values, not for event names,
  property names, IDs, platform names, versions, or environment names.
- SDKs should intern strings in first-use order to avoid a sort pass.
- Capture must reject any string table index that is out of range.

### Batch Context

Batch context stores values shared by every event in the message. Capture
expands promoted context fields into each event's `properties` map before
storage and downstream delivery.

```text
context_count uvarint
repeat context_count:
  context_key_id uvarint
  value
```

Context keys:

| ID | Name | Value Type | Required | Promotion |
|---:|------|------------|----------|-----------|
| 1 | distinct_id | string ref | Yes | top-level event field |
| 2 | $device_id | string ref | Yes | property |
| 3 | $device_model | string ref | Yes | property |
| 4 | $firmware_version | string ref | Yes | property |
| 5 | $sdk_platform | string ref | Yes | property |
| 6 | $sdk_version | string ref | Yes | property |
| 7 | $environment | string ref | Yes | property |
| 8 | $session_id | string ref | No | property |
| 9 | device_time_source | uint | No | ingest metadata |
| 10 | capabilities | uint | No | ingest metadata |
| 11-127 | reserved | - | No | - |
| 128+ | extension | value | No | ingest metadata |

Context key IDs must be unique. Required context keys must be present exactly
once. Capture must reject duplicate context keys.

`device_time_source` values:

| Value | Meaning |
|------:|---------|
| 0 | unknown |
| 1 | realtime clock |
| 2 | monotonic plus boot epoch |
| 3 | gateway assigned |

### Events

```text
event_count uvarint
repeat event_count:
  event_name_ref uvarint
  time_delta_ms  svarint
  property_count uvarint
  repeat property_count:
    property_key_ref uvarint
    value
```

`event_name_ref` is an index into the string table. It must reference a
non-empty string.

`time_delta_ms` is signed and relative to `base_time_ms`. Capture computes:

```text
timestamp = base_time_ms + time_delta_ms
```

This allows efficient encoding for tightly grouped events while still
supporting late-arriving queued events.

SDKs must preserve event time, not upload time. If an event was queued while
only boot-relative time was available, the SDK normalizes that event to
realtime once a realtime clock becomes valid and marks the message context with
the resulting `device_time_source`.

`property_key_ref` is a compact key reference:

```text
reserved key: (reserved_property_id << 1)
custom key:   (string_table_index << 1) | 1
```

`0` is invalid.

Reserved property IDs:

| ID | Property | Notes |
|---:|----------|-------|
| 1 | $battery_level | int 0-100 |
| 2 | $wifi_rssi | int dBm |
| 3 | reset_reason | string ref |
| 4 | state | string ref |
| 5 | previous_version | string ref |
| 6 | new_version | string ref |
| 7 | session_name | string ref |
| 8-127 | reserved | Requires a spec update |

SDKs must not repeat promoted message context properties in each event. Capture
adds them during expansion.

Custom property names must not exactly match any reserved property name or any
promoted context property name. Capture must reject reserved-name aliases such
as a custom string-table key named `$device_id`, `$sdk_version`, or
`$battery_level`.

### Value Encoding

Each value starts with a one-byte type tag:

| Tag | Type | Payload |
|----:|------|---------|
| 0x00 | null | none |
| 0x01 | false | none |
| 0x02 | true | none |
| 0x03 | uint | uvarint |
| 0x04 | int | svarint |
| 0x05 | float32 | 4 bytes little-endian IEEE 754 |
| 0x06 | float64 | 8 bytes little-endian IEEE 754 |
| 0x07 | string ref | uvarint string table index |
| 0x08 | bytes | length uvarint, raw bytes |
| 0x09 | array | item_count uvarint, then values |
| 0x0a | map | pair_count uvarint, then key refs and values |
| 0x0b-0xff | reserved | reject |

Map keys use the same key reference encoding as event properties. Map keys may
reference custom string-table keys. Reserved property IDs keep their reserved
meaning inside nested maps.

Capture must reject:

- NaN and infinity float values;
- arrays or maps nested deeper than 8 levels;
- duplicate keys within the same map;
- bytes values unless the project explicitly enables binary properties;
- reserved value tags.

SDKs should encode integers using the smallest semantic type that preserves the
source value. For example, `42` should be `uint`, `-1` should be `int`, and
floating point values should not be used for integer counters.

## Expansion To Event Model

After decoding, capture expands each compact event into the canonical Honch
event model:

```text
{
  "event": "<event name>",
  "distinct_id": "<context distinct_id>",
  "timestamp": <base_time_ms + delta>,
  "properties": {
    ...promoted context properties,
    ...event properties
  }
}
```

Event properties override promoted context properties only when the key is not
reserved. For reserved promoted keys such as `$device_id`, `$sdk_platform`, and
`$sdk_version`, capture must reject an event-level duplicate rather than allow a
conflicting value.

Relay metadata from HTTP headers is stored as ingest metadata and may also be
added to event properties using the existing relay promotion rules.

## Limits

Default SDK limits:

| Limit | Default |
|-------|--------:|
| events per message | 50 |
| compact message bytes before chunking | 4096 |
| string table entries | 128 |
| string bytes per entry | 512 |
| total string table bytes | 2048 |
| properties per event | 64 |
| nested value depth | 8 |

Capture hard limits:

| Limit | Default |
|-------|--------:|
| compact message bytes before chunking | 1 MiB |
| frame body bytes | 64 KiB |
| events per message | 500 |
| string table entries | 4096 |
| string bytes per entry | 4096 |
| total string table bytes | 256 KiB |
| partial message TTL | 24 hours |

SDKs may choose smaller limits per port. Capture limits are deployment
configuration, but must never be lower than the SDK defaults for official SDKs.

## Response Codes

| Code | Meaning | SDK Behavior |
|-----:|---------|--------------|
| 202 | Non-final chunk stored | Send next frame |
| 204 | Complete message accepted | Confirm/remove queued message |
| 400 | Malformed frame or message | Drop message and log |
| 401 | Invalid project key | Drop message, stop retrying until config changes |
| 404 | Unknown endpoint or stream | Drop message and log |
| 409 | Offset, duplicate, or message collision | Abort and retry from offset 0 |
| 413 | Frame or message too large | Drop message and log |
| 415 | Unsupported content type | Drop message and log |
| 422 | Semantic validation failed | Drop message and log |
| 429 | Rate limited | Retain message and retry with backoff |
| 5xx | Capture error | Retain message and retry with backoff |
| Network error | Connection failed | Retain message and retry with backoff |

## Retry Strategy

The retry strategy is:

- initial backoff: 1 second;
- max backoff: 5 minutes;
- jitter: +/-25%;
- reset backoff after a complete message is accepted.

For multi-frame transports, retry starts from offset `0` after any error that
does not return `202` or `204`.

## Canonical Encoding Rules

SDK encoders must produce canonical compact messages:

- use the exact grammar in this document;
- use unsigned varints for nonnegative integer fields;
- use ZigZag varints for signed deltas and signed integer values;
- intern every event name, custom key, and string value in the string table;
- encode message context before events;
- do not encode promoted context properties per event;
- do not emit duplicate keys in context, properties, or maps;
- set all reserved bits to zero;
- use final-frame CRC16 over the compact message bytes.

Capture decoders must be strict. They should reject non-canonical messages
rather than normalize them silently.

## Security And Robustness

- The project key is authenticated before capture stores or decodes partial
  chunks.
- Partial chunks are scoped by project, stream ID, source type, and message ID.
- Capture must bound all allocations before reading payload bytes.
- Capture must stream CRC verification and avoid copying complete messages when
  possible.
- Capture must not decode a compact message until final CRC passes.
- Capture must treat malformed varints longer than 10 bytes as invalid.
- Capture must reject integer overflow when computing offsets, lengths, or
  timestamps.
- SDKs must not include secrets in properties or context.

## Capture Implementation Requirements

Capture accepts this format on `POST /capture`.

Required capture units:

- HTTP route for `POST /capture`;
- project-key authentication using `X-Honch-Project-Key`;
- chunk frame parser;
- partial chunk store with TTL and duplicate detection;
- CRC16 verifier;
- compact event message decoder;
- string table validator;
- context validator;
- event expander into the existing event model;
- conformance fixture runner for known byte payloads.

Capture should store the original compact bytes only for debug sampling or
dead-letter diagnostics. The canonical persisted analytics event remains the
expanded event object.

## SDK Implementation Requirements

SDKs need dedicated compact-wire encoder modules.

Required SDK units:

- varint encoder;
- ZigZag signed integer encoder;
- CRC16/CCITT-FALSE;
- string table builder;
- compact value encoder;
- event message encoder;
- chunk packetizer;
- transport adapter for `/capture`;
- conformance fixture generator.

No alternate upload path is exposed by SDK transports.

## Relay And Gateway Behavior

Gateways should validate chunk frames before acknowledging a device. They do not
need to decode compact event messages unless they are applying local policy.

A gateway may either:

- forward received frames unchanged to capture; or
- reassemble the compact message locally and re-chunk it for the capture upload.

If the gateway re-chunks, it must preserve the compact message bytes exactly.
It may choose a new message ID and stream ID for the capture-side upload.

Relay metadata is carried in headers on the capture upload and is not inserted
into the compact device message.

## Conformance Fixtures

The spec requires binary fixtures before implementation is considered complete:

- one single-frame message with one event and only required context;
- one single-frame message with custom properties and repeated string values;
- one multi-frame message split at a non-value boundary;
- one duplicate continuation accepted by the reassembler;
- one CRC failure rejected before decode;
- one semantic failure for duplicate reserved property keys;
- one maximum-SDK-limit message;
- one scalar value-types fixture covering bytes, float32, and float64;
- one metadata-context fixture covering `device_time_source`, `capabilities`,
  and extension context.

Each fixture must include:

- hex bytes for every frame;
- decoded compact message fields;
- expanded event JSON;
- expected capture response code.
